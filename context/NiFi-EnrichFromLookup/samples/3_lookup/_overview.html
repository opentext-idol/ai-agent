A lookup ties everything together. Each one names a metadata definition (which fields to read from / write to the document), one or more data sources via data_id, and two ordered transform lists: inputs (build the query key) and outputs (shape the matched row before writing it back). 

document XML  --(metadata read)-->  field map
field map     --(inputs)-->         query key
query key     --(data source)-->    matching row
matching row  --(outputs)-->        result values
result values --(metadata write)--> document XML

The id of a lookup is what the processor's Lookup Identifiers property selects to run. metadata_id and data_id reference other blocks by their id; data_id may be a single id or an array (queried in sequence, results merged into the key map between sources).

inputs

Each input maps a logical field name to the value sent to the data filter. Entries are ANDed together. The bare-string form "postcode" passes the field through unchanged; the object form applies a NiFi expression and optional validation:

  • name - the metadata field name the value comes from.
  • expr - a NiFi EL expression to transform it (optional). An expression that reads nothing from the document - e.g. ${literal('US')} - injects a constant key, so no matching document element is needed.
  • required - if true, an empty final value routes the document to failure.
  • pattern - a Java regex the value must match (after expr); a mismatch routes to failure.

outputs

Each output maps a result name (which must be a field in the metadata definition) to the value written back. The bare-string form writes a column through unchanged; the object form derives a value from one or more columns via NiFi EL - for example concatenating name parts, or formatting a POINT(lon lat) geo-point.

See the Expressions sample group for the common EL patterns used in inputs and outputs.
